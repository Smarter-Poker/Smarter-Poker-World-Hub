<purpose>
Verify assigned features against actual observable behavior and preserve the results in the existing UAT.md/checkpoint. Read root AGENTS.md, the operating law, hardening standard and PUBLISHING.md first.
</purpose>

<process>
1. Recover the current task, owned revision, existing verification record and pending operation identities. Verify that the test target contains the assigned change.
2. Derive expected outcomes from the actual requirements, including affected callers and realistic failure conditions. Do not invent new product scope.
3. Run the applicable existing checks and directly observe the affected browser/API/database behavior through supported authorized tools. Use isolated test identities and preserve production users, games and financial records.
4. Record each check's exact input, expected result, observed result and evidence. Empty output, no user response, an approval phrase or a source-only assertion does not count as passing.
5. Reproduce failures safely where possible, compare the last successful equivalent and repair the authoritative cause. Recheck affected inputs and retain proportionate regression coverage in the existing directly triggered verification path. Do not force-proceed, skip required checks or remove unresolved requirements to obtain completion.
6. If a capability is unavailable, inspect configured access and documented metadata first. Perform necessary assigned configuration repairs without another approval, preserving identity, secret handling and actual tool constraints. Request only an unavailable input or explicitly required tool handoff, naming its source. Continue all independent work.
7. The owning agent personally completes executable verification and delivery. Optional assistance requires existing delegation authority, and another chat is not a release gate.
8. Record source, local tests, required hosted checks, protected merge, installation, publication and live behavior separately. Follow PUBLISHING.md through the applicable final result. Mark UAT complete only when all required outcomes are supported by actual evidence; otherwise retain exact outstanding checks and blockers.
</process>

<communication>
Provide concise material progress and a self-contained final result. User observations can add evidence or correct requirements, but are not a mandatory approval stage. No recurring task, watcher, background repair loop or new publisher may supply missing correctness or finish the release.
</communication>
