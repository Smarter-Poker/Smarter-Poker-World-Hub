# Deployment repair provider faults enter the operational inbox

Dan requested all operational failures and recoveries be routed into his existing Codex alert task, with no operational SMS. The deployment repair handler imported Twilio but its billing notification was commented out, leaving that branch as logs only. A successful secondary provider could therefore conceal the primary provider failure from the durable operational inbox. This is a verified source coverage gap, not evidence that a provider currently has a billing problem.

The authenticated handler now records primary and secondary HTTP, transport, timeout and empty-response failures through the existing service-only operational alert RPC. Stable event identity scopes retries by deployment, commit, attempt, file, provider and failure fingerprint. Provider response bodies, source code, credentials and phone numbers are omitted. A successful fallback does not mark a provider incident resolved.

An unacknowledged or malformed inbox receipt stops processing with retryable HTTP503. That error survives the per-file catch and the aggregate result selection, so an earlier successful repair cannot hide it. The authenticated deployment webhook caller preserves the retryable failure. Existing provider choices, GitHub repair rules, deployment recovery subscription and customer messaging remain unchanged.

Validation: 37 real-handler operational delivery contracts pass. Five of the six new handler tests fail against the previous source. Tests cover receipt-before-fallback ordering, retry identity, distinct failures, a later receipt failure after an earlier repair, invalid receipts, transport/empty responses, unauthorized callers and end-to-end503 propagation. External provider requests and GitHub writes are simulated in tests; no live repair, SMS or paid provider call was invoked. The contract suite is part of the existing required Build Safety Gate. Normal PR checks, Vercel READY and served commit verification are required before calling this release deployed.
