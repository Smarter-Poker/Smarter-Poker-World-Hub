# 2026-09-09: the receipt reader stopped being a model, and shipped broken once

Agent: cowork-ocr (Claude). Continuation of the 2026-09-08 receipt-scanner
handoff. PRs #1666 and #1667.

## Why the reader was replaced

Dan: "NO, WE CAN'T USE ANY AI READERS... THIS NEEDS TO BE SELF CONTAINING AND
OUR OWN DETERMINISTIC ENGINE AND READER."

The old path photographed a player's receipt, often a W-2G, and posted it to a
vision model. Four faults, only one of them cost:

- the same receipt could come back different twice;
- the feature died the day a model id was retired, twice in one week
  (`grok-2-vision-latest`, then `grok-2-vision-1212`);
- every scan cost money;
- a tax form left the building to be read on somebody else's computer.

## What replaced it

- `src/lib/docscan/ocr.mjs`: Tesseract (Apache-2.0) compiled to WebAssembly,
  served from `/tesseract` on our own origin. Never a CDN: tesseract.js
  defaults every asset path to jsdelivr, which would have put a tax form
  through a third party and broken the day that CDN did. About 6.8 MB
  downloaded once per device (one core, chosen at runtime from three, plus the
  2.9 MB English model), then cached. Offline and free thereafter.
- `src/lib/bankroll/receiptParser.mjs` and `dealerDocParser.mjs`: pure rules.
  Scored evidence, strong 3 and weak 1, a type claimed only on one strong or
  three weak phrases, `unknown` and low confidence otherwise, which routes to
  the manual choice rather than filing money in the wrong column. Every phrase
  matched on WHOLE WORDS.
- `pages/api/bankroll/scan-receipt.js` and `scan-dealer-document.js` take TEXT.
  They exist for two reasons: the `bankroll_pro` gate lives there, and the
  player's saved venues live there. Matching "BELLAG10 P0KER ROOM" against the
  Bellagio they have played fifty times is the one thing this reader does that
  a general model could not.

## Five defects found while building it

Each one a wrong number on a real receipt, each now a named regression test.

1. `TOTAL` matched inside `SUBTOTAL`: a 177.73 dinner filed as 138.00.
2. The saved venue "Aria" matched inside the server's name "MARIA": a
   steakhouse check filed at the Aria poker room.
3. Labels were tried line-first, so a stub asked for NET PAY returned the
   GROSS PAY printed above it.
4. The tournament name read the header, giving "ENTRY RECEIPT" instead of the
   event.
5. An Uber receipt (four lines and a total) scored 1 and fell through to
   `unknown`, the most common expense a player photographs on a trip.

## The one that shipped: #1666 deployed with no engine at all

`vercel.json` sets its own `buildCommand`, and it calls `next build` directly.
npm does not run the `prebuild` hook for a command nobody asked it to run, so
the asset copy wired into `prebuild` never happened in the deployed build.

Measured on production sha `453cbea689`:

```
GET https://smarter.poker/tesseract/worker.min.js                     404
GET https://smarter.poker/tesseract/lang/eng.traineddata.gz           404
GET https://smarter.poker/tesseract/tesseract-core-simd-lstm.wasm.js  404
```

Every check was green. CI does not deploy, and the local `npm run build` used
to verify DOES run `prebuild`.

Pointed at missing assets in a real browser, the engine rejects in 27 ms with a
NetworkError; it does not hang. `runOcr` catches it, the image still uploads,
the scan is still recorded, and the sheet falls through to the manual choice
with confidence 10. So every scan would have quietly asked the player to file
it by hand, looking exactly like a reader that had tried and failed, with
nothing in the logs to say the engine had never been there.

Fixed in #1667: the copy runs first in the Vercel `buildCommand`, before
`next build`. Pinned by `the engine is generated by the build that actually
deploys`, which was checked against the `vercel.json` that shipped and fails
on it.

## A ratchet that could not see what it was guarding

`scripts/ci/check-public-budget.mjs` walks the checkout, and `public/tesseract`
is generated. The 14.1 MB would have been deployed on every build and been
invisible to the guard whose entire purpose is that nothing arrives unnoticed.
It now measures the generated assets from `node_modules` whether or not the
copy has run, and CI reports:

```
public/ is 268.9 MB across 1823 files (+ 14.8 MB generated into public/tesseract at build time).
budget:  272.0 MB across 1850 files.
```

The budget was raised 260 -> 272 MB in #1666, said out loud in the file that
records it. That file's rule is THE NUMBER GOES DOWN; this is the first raise,
and the reason is written next to it.

## Verified

- 86 unit cases across the two parsers: every document type, every expense
  category, the glyph-confusion venue match, junk, empty and hostile input,
  and each of the five defects above.
- A real browser running the real generated assets through the real engine:
  four receipts drawn on a canvas, read at 260-480 ms each, and the text the
  engine ACTUALLY produced fed to the parsers. 18/18.
- On PRODUCTION, after #1667: the deployed engine fetched
  (`worker.min.js`, `tesseract-core-relaxedsimd-lstm.wasm.js`,
  `lang/eng.traineddata.gz`, all 200) read a tournament receipt in 704 ms at
  engine confidence 94, and the parser returned buy-in 300, fee 40, total 340,
  venue Bellagio. One core was fetched, not three, which is the runtime
  selection working.

## Not proven on hardware

No phone, no camera and no physical W-2G. The engine was exercised in headless
Chromium against canvas-rendered receipts. That is real OCR on the real
deployed assets, but it is not a photograph taken in a poker room.
