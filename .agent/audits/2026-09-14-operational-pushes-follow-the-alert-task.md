# Operational push notifications follow the owner's incident task

The SMS cutover left two push paths active: database notifications mirrored into `push_outbox`, and immediate sends through `enqueuePush`. An actual `guarantee_bank_short` notification was recorded as sent after the cutover, September 13 at 17:03 UTC. The failed-break SQL producer also still targets the owner's active recipient record. Push-health reports use the immediate path. Altering only the SQL mirror would leave that path open.

The correction intercepts the owner's reviewed operational notification types before immediate preference/force gates and before queued age/preference suppression or digest formation. Each original outbox ID becomes a separate, idempotent operational-inbox event for task `01a09b86-5ba8-7290-8657-1041f13dd3ca`. Recovery types follow the same destination. A receipt from the task is recorded as routed, with zero phone deliveries. Failed/malformed receipts retain durable pending rows and never fall through to a phone sender. A large dispatcher batch is split at the existing 200-event inbox boundary.

The filter covers financial incidents/attestations, failed and recovered maintenance breaks, guarantee-bank warnings/recoveries, estate diagnostics, and the actual legacy Push Health Alert/Horse Fleet system templates. It applies only to the verified owner account. Customer messages, invoices, seat offers, revenue summaries, account-security notices, and other recipients retain their existing behavior. New operational producer types must be added to the reviewed classifier and the task's historical readers together.

The independent task readers `evidence/reconcile-owner-operational-notifications.sql` and `evidence/reconcile-owner-operational-push-history.sql` retain notifications and outbox rows from the requested backlog, including sent, skipped, pending and exhausted records. They provide durable intake while a delivery process is offline or cannot obtain another queue claim. These task-side statements do not modify notification history or source incident state.

Local verification executes the actual immediate and dispatcher entrypoint bodies with controlled external I/O, including force overrides, missing push configuration, original per-event evidence, recovery, stale notices, batch splitting, partial failures, malformed receipts, failed finalization, stable replay identity, complete persistence failure and ordinary customer delivery. Run `node --test __tests__/operational-push-routing.test.mjs __tests__/operational-alert-inbox.test.mjs __tests__/native-push-fcm.test.mjs __tests__/push-hardening.test.mjs`.

The follow-up audit found that legacy `system` events titled `Horse Fleet Recovered: ...` were routed correctly but classified as firing, because the status mapping recognized only typed recovery suffixes. The mapping now preserves their resolved status without treating body text or unrelated titles as recovery. A regression test first reproduced the error and now verifies distinct original identities, original evidence, and the expected firing/resolved/firing sequence.

The independent helper review also found three concrete gaps. Missing VAPID credentials returned before the dispatcher could route database-produced operational notices; a bounded operational-only query now routes those originals without claiming customer rows or spending their retry attempts. Failed or malformed reads return a retryable failure. Raw alternate UUID spellings from the admin endpoint could bypass a strict string comparison; the owner comparison now uses the same underlying UUID identity for uppercase, compact, braced and grouped spellings. Finally, the sending API counted failure of both durable stores as a queued success. It now returns HTTP 503 with the exact failed recipients for targeted retry and preserves accurate delivered/queued/skipped counts for the other recipients.

The combined Node checks include those cases and execute the actual sending API with the real operational enqueue failure path. Linked notification severity is now preserved only after verifying its ID, recipient, event, and mirrored title/body against the original push. Metadata lookup is bounded and abortable; a lookup failure still stores the original incident with explicitly unresolved metadata. Unknown severity remains a warning pending classification review. Caller-supplied severity is never trusted, and the original push is unchanged.

The complete local command is `node --test __tests__/operational-push-routing.test.mjs __tests__/operational-push-metadata.test.mjs __tests__/operational-alert-inbox.test.mjs __tests__/native-push-fcm.test.mjs __tests__/push-hardening.test.mjs __tests__/notifications-send-operational-persistence.test.mjs` (81 passing checks). The two exact backlog reader SQL classifiers were corrected separately in the alert task; 99 native SQL assertions verify original identity, recovery status and linked severity. These changes do not repair an already-created inbox record, since receipt replay changes only delivery counts and timestamps. Existing unresolved metadata requires an explicit evidence-based classification update. The reviewed recovery affected-ID query returned zero rows; the separate severity review found 33 warning records with exactly matched critical source notifications.

This source candidate has not been deployed. Required release/build qualification and natural production delivery evidence remain open. No phone test, production push mutation or GitHub operation is part of this local correction. The separate zero-shortfall guarantee-bank notice still requires its own root-cause investigation.
