SMARTER.POKER SIGNED SOLVER WORKER DEPLOYMENT
=============================================

The former God Mode direct-ingest path is permanently retired.
`scripts/ingest_god_mode.py` is a fail-closed tombstone and must not be copied,
wrapped, scheduled, or restored. M1 and M2 must never hold any Supabase URL,
anon credential, service credential, or database connection string. Remove all
legacy values from machine/user environment settings, `.env` files, scheduled
tasks, wrappers, and shell profiles. Rotate any historically exposed database
credential centrally before either worker is enabled.

The only supported publisher is:

    scripts\preflop-deep\run_machine.py

It sends bounded HMAC-authenticated requests to exactly:

    https://smarter.poker/api/training/solver-worker

Operator-controlled prerequisites
---------------------------------

1. Deploy the protected signed-worker API and migrations first.
2. Keep the solver provenance allowlist empty until the binary, protected
   pipeline commit, manifest, target ledger, and pre-existing UUIDs have been
   independently verified under the admission runbook.
3. Provision two different 32-byte HMAC secrets in the authorized secret store:
   one for M1 and one for M2. Give each host only its own secret. Never copy one
   host's value to the other and never store either value in this repository.
4. Install the approved PioSOLVER console executable and independently record
   its SHA-256. Install the approved range directory and checksums.
5. Disable every legacy task or wrapper before the supervised canary.

Required per-process environment names
--------------------------------------

    SOLVER_WORKER_API_URL
    SOLVER_WORKER_HMAC_SECRET
    PIO_EXE
    PIO_SOLVER_VERSION
    APPROVED_PIO_BINARY_CHECKSUM
    PIPELINE_COMMIT
    APPROVED_MANIFEST_CHECKSUM
    RANGE_DIRECTORY
    SOLVER_RELEASE_BUNDLE_DIRECTORY

The HMAC value must come from the authorized per-host secret store. Do not echo
it, pass it on a command line, put it in a batch file, or persist it with SETX.
The launcher validates the exact endpoint, manifest, protected pipeline bundle,
range files, and Pio executable before starting solver work.

Controller-delivered release bundle
------------------------------------

Run the builder only on a trusted POSIX controller using macOS or Linux. It is
not supported on Windows, and M1/M2 must never execute it. Windows solver
workers consume the controller-delivered exact five-file directory only.

On that trusted controller, build the five-file directory from immutable Git
object bytes with `scripts/preflop-deep/build_release_bundle.py`. Supply an
exact protected-main ancestor commit, the independently observed 40-character
protected-main commit through `--protected-main-commit`, a new absolute output
directory, and the independently verified Pio version/binary checksum. The
builder requires its canonical `refs/remotes/origin/main` to equal that separate
controller attestation; refresh and verify the canonical remote before running
it. The builder rejects dirty
working-tree substitution, non-ancestor commits, symlinks/reparse points,
pre-existing output, Git replacement/graft/environment substitution, corrupt object
bytes, missing payloads, oversized files, and checksum drift. Its JSON receipt
records the controller-attested protected-main commit and contains no HMAC or
database credential.

The worker must not fetch source from private GitHub raw URLs. It has no
GitHub credential and no network fallback for pipeline distribution.

On the controller, independently verify a protected 40-character commit and
all required framework ancestors. Read the five exact Git blob byte streams
from that commit: phases.json, run_machine.py, tree_gen.py, pio_harvest.py and
orchestrate.py from scripts/preflop-deep. Preserve LF bytes on Windows; do not
package checkout files that Git has converted to CRLF.

The protected phases.json must declare
pipeline_distribution="controller-local-bundle.v1", pipeline_files_sha256
with exactly the four Python filenames and their SHA-256 values, and the
existing pipeline_bundle_checksum. The aggregate is SHA-256 over each filename,
a NUL byte, exact file bytes, and a NUL byte, in this order:
run_machine.py, tree_gen.py, pio_harvest.py, orchestrate.py.

Deliver these five files through the approved controller delivery mechanism
to a new local bundle directory. Set SOLVER_RELEASE_BUNDLE_DIRECTORY to its
absolute path, and provision PIPELINE_COMMIT plus APPROVED_MANIFEST_CHECKSUM
from the independently verified protected release record. Never derive the
approved checksum from the received directory itself. The worker rejects
missing or extra files, redirected paths, non-regular files, oversized files,
changed manifest bytes, per-file mismatches, aggregate mismatches, and a
running launcher that differs from the sealed source. All checks precede
pipeline imports, gateway requests and Pio startup. Install the launcher into
a separate new release directory; do not overwrite a legacy solver directory.
The launcher supplies the verified manifest bytes to the orchestrator, which
rechecks the same checksum for canary and backlog reads. It never re-downloads
a manifest or picks up a new release in place during an active run.

This transport change does not approve a solve. Keep solver_ready=false and
bounded_canary_ready closed until the separate host, Training ledger, ranges,
target identities, HMAC provisioning and database authority gates pass.

The provisioning controller must launch the worker with an explicit minimal
environment, rather than inheriting its own database credentials. Include
only required Windows runtime variables and the approved worker settings
listed above. Supply the machine-scoped HMAC through the approved in-memory
mechanism only. The runner's database-variable rejection remains mandatory;
do not remove that rejection or treat filtering as proof of whole-host
credential sanitization. User/machine/task/file scopes require separate audit.

Safe validation and launch
--------------------------

From the protected repository checkout, run the non-mutating environment check:

    scripts\windows-setup.bat M1

or:

    scripts\windows-setup.bat M2

The check never connects to Supabase and never starts the solver. After the
operator gate is complete, start exactly one supervised canary:

    python scripts\preflop-deep\run_machine.py M1 2 0 --canary

For M2, only after M1's signed heartbeat and exact parent/child admissions are
verified:

    python scripts\preflop-deep\run_machine.py M2 2 1 --canary

The default backlog runner still requires `release_gate.solver_ready=true`.
That backlog gate may remain false while a deliberately bounded canary is
enabled by the independent `release_gate.bounded_canary_ready=true` gate. In
that state, run only the explicit `--canary` command above; never start the
default backlog loop. Do not enable either mode while its applicable gate is
closed, while the target ledger has a missing or duplicate UUID, or before the
external credential-rotation and provenance-approval steps are complete.
