# Correction records in Messenger

Source candidate only. All tests and application qualification are **UNRUN**. This document does not establish installed schema, deployment, delivery, historical repair or accounting completion.

The existing Accounting Invoice card recognizes `accounting_correction` only through the existing private message reader's canonical invoice/provenance projection. Its separate proof must contain a matching invoice, source journal leg, required real club UUID and explicit nullable union UUID, positive fixed-two-decimal string amount, `generated` status, false chip-transfer flag, and explicit null due/transfer timestamps. An unscoped union-only public receipt is refused: the actual invoice table requires a real club foreign key. Original nullable journal scope remains separate private provenance. The nested version-1 correction contract retains distinct UTC journal-recorded and document-issued timestamps, with `payment_proven=false`, `new_chip_movement_claimed=false`, and `original_payment_invoice_id=null`.

The card displays **Correction Recorded**, **Correction amount**, and **Recorded**. Its description is: “A correction was recorded in the accounting journal. This record does not establish a new chip payment.” It does not infer a payable debt, a new payment, an original payment link or incident closure. An unavailable or mismatched typed proof shows **Receipt unavailable** and an unavailable amount. Existing old paid correction metadata is not enough to obtain this proof.

The message verifier removes incoming `correction` and `correction_verified` metadata before handling the server receipt. A canonical correction forces the existing `accounting_invoice` kind and a strict metadata whitelist, so copied `union_invoice`, outstanding totals, weekly lines, arbitrary invoice numbers, private reasons, actors, incident IDs and balances cannot turn it into a debt summary or leak through the card. Correction content and preview text use the deterministic safe description, or the unavailable description. Metadata alone cannot grant verification. The existing generic and weekly paths remain intact, and cashier Held/Approved/Returned meanings are preserved.

`get-messages` passes the private reader's correction, scope and due/transfer fields into that proof. It introduces no new database query, reader, role grant, message writer, payment action or push dispatcher. Database provenance and audience enforcement remain in Club Arena's additive component34. In particular, WH does not broaden immediate club-to-individual correction visibility to club admins or add individual correction amounts to weekly club movement totals.

Historical identity uses a separate private-reader assertion: `invoice_identity_verified=true`, `correction_unverified=true`, `accounting_verified=false`, and `correction_verified=false`. It retains only the actual invoice UUID/type, source ledger UUID, real invoice club UUID and explicit nullable source union UUID. No amount, status, transfer flag, payment dates or nested correction proof is accepted in that envelope. The server must prove the existing invoice/message/delivery/recipient/source-category joins. WH strips copied identity flags, validates the separately supplied projection and renders **Receipt Unavailable**, with “Correction receipt unavailable.” content. Accounting verification remains false and the original invoice type remains unchanged. Invalid identity assertions cannot fall through into ordinary paid verification. Arbitrary diagnostic or balance metadata is excluded.
