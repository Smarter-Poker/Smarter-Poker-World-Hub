# Cashier receipt display contract

Source candidate only. Tests and application builds are **UNRUN**. This change does not install the matching Club Arena database component, schedule expiry, or prove delivery to a device.

The existing Messenger invoice card displays three cashier outcomes: **Chips Held**, **Cashout Approved**, and **Chips Returned**. The approval describes chips transferred to the approving cashier. Cancellation, decline and expiry describe chips returned to the player's wallet. The card uses neutral wording because the player, cashier and deliberately included frozen club-owner representative can all receive it. It contains no private wallet balances, source UUIDs, raw metadata, or external cash-payment claim.

The Club Arena additive cashier component must return a canonical `cashier_cashout` invoice projection from the existing private message reader. `get-messages` passes that projection as the separate server receipt to `verifyAccountingMessage`; no request-body metadata or additional database query grants receipt authority. The required top-level fields are `accounting_verified`, `cashier_verified`, invoice ID/type/status, `chips_transferred`, `source_ledger_id`, `club_id`, amount and nested `cashier`.

Nested contract version 1 includes event, invoice, cashout, escrow, source transaction, source ledger, club, player, assigned cashier and frozen issuer representative IDs; actual actor ID/role; event kind/display state; exact amount; occurrence and issuance timestamps; original hold event/invoice IDs; physical ledger endpoint types and entity IDs; and explicit custody/completion/refund booleans. The parser validates the exact invoice/source/club/amount joins and these relationships:

| Event | Invoice status / transfer flag | Actor and physical route | Display |
|---|---|---|---|
| `hold` | `generated` / false | Actual requester, player wallet to escrow; hold links null | Chips Held |
| `approval` | `paid` / true | Actual authorized cashier, escrow to that cashier's agent wallet | Cashout Approved |
| `cancellation` | `paid` / true | Requester, escrow to original player wallet | Chips Returned |
| `decline` | `paid` / true | Actual authorized cashier, escrow to original player wallet | Chips Returned |
| `expiry_refund` | `paid` / true | Null user with `system` role, escrow to original player wallet | Chips Returned |

Every terminal event links to a distinct original hold event/invoice. The hold document stays a held-chips document after a terminal event occurs. The parser preserves both timestamp strings, including microseconds, and validates calendar/time syntax. It accepts positive fixed-two-decimal cashier amounts within the existing `settlement_invoices numeric(12,2)` storage range and formats them without floating-point arithmetic.

Raw cashier flags and payloads are removed before normalization. Missing or inconsistent cashier proof retains a known invoice's identity but renders **Receipt details are unavailable**, without a paid/held/refunded claim or its raw content. With no server invoice receipt, a submitted invoice-shaped message remains unverified text. Generic invoices and weekly club summaries keep their existing display/status behavior. No individual rakeback receipt is added to the club's weekly summary audience by this UI change.

`__tests__/cashier-accounting-display.test.mjs` covers all five phases, exact cents, source/actor/status mismatch, missing hold links, forged metadata, invalid or oversized amounts, date validation, safe rendering, generic/weekly compatibility and the existing authenticated API proof mapping. The existing accounting UI test's module loader is adapted for the shared parser import. These tests are source only and require the protected local pipeline; they have not been executed.

The matching CA source owns event validation, atomic money/document rollback, frozen recipient membership, canonical projection and actual permissions. Unsupported departed-player refunds and old holds without verified evidence must fail closed there; this renderer cannot create a refund or historical receipt. In root's separate retained metadata read, `cron.job WHERE command LIKE '%fn_expire_stale_cashouts%'` returned no rows. That establishes no matching direct command in that capture, not the absence of an indirect or external scheduler. This display change makes no scheduling claim.

## Legacy HTTP callers now use the same cashier authority

The three World Hub routes `request-cashout`, `approve-cashout`, and `cancel-my-cashout` call the Club Arena V2 authority with an anonymous-key client carrying the original verified Bearer token. The service client remains limited to existing gate reads, horse approvals, and audit recording. It never supplies the cashier actor or calls a legacy cashout financial writer. No ordinary Messenger message or secondary push is emitted by these routes; the canonical database transaction owns the receipt, private delivery, and notification outbox.

Every request now requires a UUID `X-Idempotency-Key` retained by the original caller and a matching `expectedActorId` in the body. The routes normalize UUID casing before dispatch. The only identified active World Hub caller is `/horses` for the staff approval/decline route; it now sends both. Existing external callers of request/cancellation need the same contract. No active literal World Hub UI consumer of those two routes was found in the bounded source audit. Club Arena's own callers use its service directly.

Before any new-money gates, the routes call authenticated `fn_cashout_operation_receipt_v2` with actor, operation, action (`hold`, `approval`, or `release`), club, amount, original nullable cashout ID, and normalized note. Only an exact `found:false` envelope with `receipt:null` allows the existing new-money path. Errors, missing resolver, malformed output, or mismatched intent refuse. Exact `found:true` requires the full canonical receipt with `replayed:true`. It confirms the historical chip event without re-running or certifying current approval/audit completion. The resolver owns no financial or document writes.

The resolver takes operation and row locks to observe a consistent committed receipt. PostgreSQL therefore declares it volatile and requires a normal transaction, rather than a transaction marked `READ ONLY`; “read-only lookup” here describes its lack of financial/document writes, not that SQL transaction mode.

New requests retain this HTTP route's existing whole-chip range of 100 through 100,000,000. New staff approvals retain enrolled-user MFA, settlement, runtime maintenance freeze, club/union/operator route gates, and the existing horse maker-checker path. Unknown gate reads refuse; a nullable MFA enabled value or nullable settlement flag is unavailable. A flagged settlement lock remains asserted until the settlement authority clears it, even when its timestamp has elapsed; these routes no longer clear locks as a read side effect. The confirmed metadata capture only establishes column names, not actual gate state or active-seat correctness.

The staff route refuses approval or decline of the actor's own request before resolver or financial dispatch. Requester cancellation uses its own route. A route-level platform or union permission never broadens the V2 database's current club cashier/downline eligibility. Pure operator/union membership is therefore insufficient to move chips. The retained legacy SQL already required cashier membership or club ownership for both staff financial writers; this is not evidence that pure platform permission previously authorized money. Old undocumented or unescrowed holds and departed-wallet refunds remain explicit fail-closed compatibility boundaries. No history is fabricated.

The V2 adapter compares the actor, operation, kind, club, player, amount, immutable accepted note, physical ledger route, every shared event identity, timestamps, and canonical current request DTO. It refuses bare success, scalar IDs, malformed dates, missing fields, number/string amount substitutions, and contradictory phases. The returned DTO uses camelCase request fields and exact amount text. Wallet balances do not leave the adapter. A replayed hold preserves the actual current terminal request state.

`/horses` hashes a canonical tuple of lowercase actor/club/cashout IDs, action, and normalized note before retaining a UUID under a Web Lock. Plaintext financial notes are not stored in the key or value. The UUID survives pending approval, uncertainty, success, and page/dialog reopening. Missing durable storage, secure random UUID, Web Crypto, or Web Locks refuses a new action; no process-memory fallback mints a new financial intent. Auth events, route events, view/dialog/read generations, and the pre/post-token fetch fences retire stale work. A timeout or local retirement does not cancel a remote transaction.

After a canonical receipt, failure or refusal to close a horse approval or persist its operator audit returns the receipt with `trailClosed:false` and follow-up required. The UI reports the confirmed chip event and unresolved follow-up; it does not redispatch money to repair the audit. The older dual-write logger has no success receipt and swallows failures, so its status remains explicitly unconfirmed. Historical receipt lookup likewise leaves approval and audit follow-up unconfirmed.

Historical lookup returns `trailStatus:'not_checked'` and `trailClosed:null`, without claiming follow-up is required or an audit failed. Only an approval replay includes `approvalStatus:'unconfirmed'`. The UI distinguishes this unchecked status from a known post-write closure failure.
